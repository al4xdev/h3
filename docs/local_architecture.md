# Local H3: the directory is the source of truth

## Owner decision

The application runs on the PC. `.data` materializes requests, states, references, chunks, and assemblies. A mobile phone functions merely as another browser accessing the PC's web interface: its uploads are stored directly in this same directory. There is no folder synchronization, database, message broker, external queue, or traditional layered backend service architecture.

```text
Browser JS (PC or mobile)
       ↕ Local HTTP: files, uploads, metadata
       ↕ SSE: path mutation notifications, not business state
Small bridge on the PC
       ↕ Own paths in .data
Worker watching the PC directory
       ↕ Subprocesses / native execution
FFmpeg / ffprobe / ComfyUI
```

The browser does not have arbitrary access to the PC's filesystem. The bridge provides restricted access exclusively to application-managed files. Selecting an existing file in `.data` versus uploading a new one represent two input pathways targeting the same underlying paths; they do not introduce a secondary authoritative catalog in JS.

## Materialized work

- An atomically published JSON file specifies an explicit intent. A `.lock` file coordinates worker execution; it never substitutes for the request itself.
- Modifying a video file, starting the filesystem watcher, or opening/reconnecting a browser page never authorizes generation.
- State and execution outputs published to paths are read by both sides. Filesystem events alert the worker; SSE invalidates frontend views, prompting the client to re-fetch the relevant path.
- Registering the filesystem observer prior to acquiring the initial state snapshot eliminates windows where mutations might be missed. Dropped events or buffer overflows require re-reading metadata, never replaying inference.
- Abandoned locks and interrupted executions preserve forensic evidence. Never assume a ComfyUI POST did not occur simply because an output has not materialized yet.
- A single dispatcher and builder coordinate operations; i2v and v2v preserve fluent composition and vertical organization. The bridge does not duplicate these workflows.

## Media kept off the Python heap

Python routes filesystem paths and manages OS processes; it does not load pixel arrays, raw images, or entire video containers into memory. Dedicated FFmpeg and ffprobe processes handle validation, frame extraction, media preparation, and assembly. Python copies, streams, and hashes encoded bytes using bounded buffers. The browser renders media using `<video>`, `<img>`, and optionally HTML5 Canvas for visual comparisons.

Pillow must not be added to the runtime. Legacy CPU-based comparison scripts are treated as isolated tooling until superseded. Never alter models, samplers, conditioning, guidance, VAEs, generation parameters, or final decode pipelines to accommodate changes in transport or validation layers.

Linux page caches and ComfyUI model/tensor allocations are independent of the orchestrator's heap. Measure RSS on a per-process basis; avoid claiming memory reductions simply due to using file locks or omitting a database.

## Explicit assembly within the same local resource limits

Backend `eaf4ba8` implements fluent composition: `AssemblyPipe(service).have(UUID).from_end(runUUID).save_video().arun()`. CPU execution uses the existing dispatcher, execution slot, and leases from generation; it avoids creating job queues, command frameworks, or Grok couplings. The legacy free-RAM check was dropped in plan 38: active assemblies and admissions are never cancelled or rejected due to available RAM. Telemetry remains observational; the app does not supervise ComfyUI scripts, processes, or memory caches. Submitting a POST with a known UUID awaits CPU completion and returns 200; client disconnection does not abort the server task. Reconnection or uncertain states trigger a GET on the same ID rather than re-POSTing. An external process crash provides no guarantee of continuity or auto-replay; errors, uncertain states, and task IDs are recorded as evidence.

`.data/assemblies/<UUID>/request.json` represents the immutable request, written last and re-read for execution. Lifecycle metadata is mutable; `video.mp4` and `output.json` are immutable evidence, committed upon `metadata.completed`. Checks on file paths, UUIDs, regular file types, UID ownership, hard link count = 1, file size, and SHA hashes prevent forged inputs; startup interrupts lingering tasks without replay. Requires the terminal chunk to be `ready` or `accepted` and all ancestral chunks to be `accepted`. Run decisions are never altered.

FFmpeg concatenates frames sequentially and pads audio up to block boundaries using the existing CRF 18 / yuv420p helper; this does NOT imply byte-identical RGB/MP4 output, nor does it guarantee facial or perceptual equivalence. 602 Python tests (521 baseline + 22 editor + 59 assembly) and 44 Node tests passed prior to final UI polishing.

Real-world audit: a single CPU assembly run (`808836a6-434d-47d8-8d2a-98d97e038385`) combining three existing `final_only` chunks produced 168 frames / 7 s @ 480×864, 24 fps, stereo AAC @ 32,000 Hz, with boundaries at frames 56/112 and HTTP 206 Range support. The third chunk remained `ready`; both parents were `accepted`. External end-to-end video and audio decoding succeeded without passing pixel buffers through Python. Evidence logged to `.dumps/tests/reports/runtime_assembly.json`; 162 protected files remained untouched. Assembly is fully supported, but an unreviewed ready tail is explicitly marked as a **preview — review pending**, not as artistic approval.
